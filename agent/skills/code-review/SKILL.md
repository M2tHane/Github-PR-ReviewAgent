# 代码审查

1. **先弄清改了什么。** 读 PR 标题、描述和 changedFiles 的 patch，说出这次改动想达到什么效果。描述和代码不一致时记在 summary，不算 finding。
2. **顺着调用链看影响。** 对改动的函数、接口和数据结构，用 `codegraph_callers`、`codegraph_impact` 或 grep 找调用方，确认调用方是否跟着改了、旧数据和旧调用是否还能工作。
3. **逐项检查：**
   - 正确性：边界值（空、零、负数、极大）、错误分支、并发与重复执行、状态是否会被旧请求回退。
   - 安全：外部输入是否校验、是否有越权、敏感数据是否进入日志或响应。
   - 模块边界：是否绕过已有的封装、复制已有逻辑、引入反向依赖。
   - 团队规则：只按 activeTeamMemories 判断，引用时用它的 id、version、source。
4. **确认后再写。** 每条 finding 都要能指出具体代码行和触发条件；说不清怎么触发的，降低 evidenceLevel 或不写。需要时可以运行不改文件的检查（类型检查、单个测试），只报告实际运行过的结果。
5. **不写的内容：** 风格偏好、没有证据的猜测、与本次变更无关的旧问题、"建议加测试"这类泛化建议。

改动涉及安全、架构或团队规则冲突时，再读对应的专项 Skill。
