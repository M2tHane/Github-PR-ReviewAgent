# PR、issue 和 issue 回复的写法

## 怎么写（三种都一样）

读的人是没参与过程、也不一定看代码的同事。读不下去的说明等于没写。

- 大白话、短句，先说结论。一句能说完不写两句。
- 只写读的人需要知道的：改了什么、为什么、要他确认什么。不写读代码的过程、用了哪些工具、函数调用链、执行状态。
- 非提不可的文件、字段、命令用反引号；别的术语换成日常说法。
- 不重复，不客套，不写“如有问题请告诉我”这类话，不写 AI 生成脚注（如 `Co-Authored-By`、`Generated with`）。
- 字数上限：PR 正文 1000 字，issue 正文 3000 字，issue 回复 1500 字。服务会检查，超了会让你压缩。

## PR 标题

```
<类型>(<范围>): <简体中文描述>
```

类型用 `feat`（新功能）、`fix`（修复）、`refactor`（重构，行为不变）、`perf`（性能）、`docs`、`test`、`chore`（构建、脚本、依赖）。范围不明确可省略，例如 `fix: 修复使用日志导出币种`。

## PR 正文

按顺序，没有的段落就不写：

1. 一两句话：解决了什么问题或新增了什么行为，关键做法是什么。
2. **同时改了：** 有次要改动时用列表列出（日志、顺带修复、配置、测试等），不凑条数。
3. **需要确认：** 需求没说明、由你按判断定下的取舍（选了哪种理解、某个值取多少、为什么加某个防护），逐条列出。
4. 影响：数据库结构是否改变、要不要迁移，部署配置、依赖或兼容性是否受影响。根据读过的代码判断；没有数据库变更写“无需数据库结构变更或迁移”，拿不准就写明待确认，不要套话。
5. 最后一行以“验证：”开头：跑了哪些检查（按范围概括，不贴命令和参数）、结果、没跑的关键检查。什么都没跑写“验证：未运行构建或测试。”

示例：

```
修复视频再生成时，同一个 API Key 仍被当成新渠道去转存的问题：补读原任务的凭据，并保存 Key 的指纹用来比对。

同时改了：

- 转存原因和上传失败时记日志，敏感信息已脱敏。
- 加了回归测试。

无需数据库结构变更或迁移，不改部署配置。

验证：视频转存相关单测通过；未运行全量测试。
```

## issue

需求有没定的地方时开 issue，把问题问清楚。标题一句话说清要做什么，不加类型前缀。正文：

```
**要做的事**：一两句话，说你理解的需求。

**需要你确认**（有异议的回复编号即可，没提到的按推荐做）：
1. ……？推荐：……（一句理由）
2. ……？推荐：……

**确认后的做法**：一两句话。
```

一次把要定的问题都列出来，编号连续，不留到下一轮再问；只问会让做出来的东西不一样的事，不凑数。推荐做法要具体到能直接照着开发。正文末尾“谁回复‘开始’”的说明由服务加，不用自己写。

## issue 回复

- 对方对某几条有异议：只回应这几条，说清改成怎么做；没提到的编号按原推荐，不再重复列出。
- 对方问了就直接答，涉及现有代码的先查代码再说。
- 对方的意见带出了新问题才继续问，接着用新编号，格式同上。
- 都清楚了，用一两句话说和原推荐不同的地方，提醒提需求的人回复“开始”。
