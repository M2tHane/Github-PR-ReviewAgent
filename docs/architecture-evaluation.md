# 架构评估与目标架构

版本：v0.1｜日期：2026-11-15｜状态：评估与设计，按阶段实施（进度见 [ARCH 清单](tasks/ARCH.md)）

> 本文从产品定位、系统架构、Agent 架构和核心工作流评估当前实现，并给出面向"多仓库、团队级 AI 工程协作系统"的目标架构与实施路线。文中 `文件:行号` 基于提交 `beea169`，代码变动后行号可能偏移。目标是两条相互关联的能力：PR Review 与工程知识沉淀、基于工程知识的 AI 开发，形成"PR Review → 知识沉淀 → 规则复用 → AI 开发 → PR → 新的 Review → 知识迭代"的闭环。

> 用户 2026-11-15 撤销独立团队层：每个仓库就是一个团队，规则只属于仓库；保留 must／should／info、上下文编译器和现有跨仓库复制导入。下文模型与阶段 2 已按此决定调整，历史问题与未采纳的远期设想不代表当前任务。

## 结论先行

1. **产品方向成立，但现在的系统还不是一个靠知识运转的闭环。** 它实际上是"PR Review 服务 + 旁边挂着的一个开发机器人"。
   - 知识闭环从没在真实数据上跑起来过：3 个合并 PR 只抽出 1 条候选规则（`docs/tasks/M1.md:95-99`），整个项目没有任何规则质量或召回率数据（`M2.md:2348`）。
   - 开发 PR 在代码里被明确排除在自动审查之外。"AI 开发 → Review → 修复 → 知识"这条线是断的。
2. **最该推翻的有三处。**
   - 知识模型只有"仓库"一个维度，跨项目只能复制。
   - 执行引擎有两套。开发任务不能恢复，而且绑死在企微连接上。
   - 开发闭环：开发 PR 不审查、没有 CI 反馈、验证只靠 Agent 自己说。
3. **最该保留的是那些由服务强制执行的约束。** 包括：固定 SHA 的工作区、Pi 进程加本地模型代理控制预算、服务端核对模型引用、发布台账加远端核对、开发改动由服务从工作区收集后再用 Git Data API 提交。这些都没有把可靠性押在 Prompt 上，目标架构全部沿用。
4. **Agent 架构：不需要用大模型做编排，也不需要多个专项 Agent 分头审查。** 编排交给确定性的工作流引擎。Agent 按"上下文、权限、输出格式各不相同"来划分：Reviewer、Reply Triage、Knowledge Extractor、Planner、Developer。其中 Planner 和 Developer 是同一个 Agent 的两个阶段。真正有价值的"多 Agent"是 Developer 和 Reviewer 互相制衡（上下文独立、用同一套规则），而不是让模型扮演不同角色。
5. **知识不等于规则。** 应分成四类：规则、设计决策、仓库画像、历史案例，四类的生命周期不同。只有规则和决策需要人批准。
6. **规则的主要来源不应该是"挖掘合并 PR"。** 证据：3 个合并 PR 只出了 1 条候选；tuzi-api 的 50 条规则是人工从文档研究出来的。产出最高的来源是：
   - 现有文档和 ADR 的结构化导入；
   - 反复出现并且被修复的审查意见；
   - 人对 AI 写的 PR 提出的修改要求。
7. **接入第二个团队之前有一道安全门槛。** 现在所有 Agent 的 bash 和服务跑在同一个系统用户下，能读到 GitHub App 私钥文件（`src/config/config.ts:101`）和 `.env`。单团队内部使用已明确接受这个风险（[NOTES](../NOTES.md)）。跨团队之后，一个仓库出问题就会波及所有已安装的仓库。

## 1. 当前架构诊断

### 1.1 真实的运行架构

```

┌───────▼──────────────────────────▼─────────────────────────▼───────────────┐

│  固定 SHA 浅克隆工作区 + Pi 进程 + 服务扩展（路径/打码/写入检查/附规则）          │

### 1.2 组件与实现状态

| 组件 | 状态 | 评价 |
| --- | --- | --- |
| PR Review：单 Agent + 4 个 Skill，只读工具 + bash（`src/review/agent.ts:204,231`） | 已实现，真实 PR 验证过 | 主体合理。分组、引用校验、修复轮、发布台账做得扎实 |
| Semgrep／密钥／OSV 扫描，结果交给 Review | 已实现 | 合理，但代码放在 `src/health/` 下，review 反过来依赖 health |
| Reply Handler（只处理本 App 的线程） | 已实现，PR #3 四种结论各验证 1 次 | 合理。它产出的"例外线索"走不到可批准的规则（见 P0-1） |
| Decision Extractor | 已实现，真实运行只产出过 1 条 | 看不到已有规则 |
| 规则库：候选→确认→版本／替代／例外 | 已实现，按仓库隔离 | 生命周期可用，但维度不够 |
| 仓库级作用域 | 每个仓库独立管理规则（[memory-design](memory-design.md) §6） | 用户已撤销独立团队层 |
| 跨项目规则 | 做成了一次性复制导入（`src/memory/import.service.ts`） | 复制后各自演化，不是共享 |
| Health + Security Auditor | 已实现，两次真实验收都是 partial | 不在两条核心能力里 |
| 开发任务（企微→PR、issue 讨论、按 PR 评论修改） | 企微→PR 真实跑通过；"按 PR 评论修改"没有验证记录（[DEV 清单](tasks/DEV.md)） | 是第二套独立的任务引擎 |
| Main／Specialist 多 Agent | 2026-11-09 已移除 | 移除有数据支持 |

### 1.3 对产品思路的判断

1. **"规则"和"知识"要分开管。** "怎么跑测试""模块怎么分"是事实，应自动生成，用实际运行来校验。"资金变更必须幂等"是规范，需要人背书。"上次这里误报过"是案例，应自动沉淀、自动衰减。全部塞进一张需要人工确认的规则表，结果是：要么维护者被淹没，要么事实类知识根本进不来。
2. **挖掘合并 PR 产出低、噪声大。** 大多数 PR 讨论里没有可以复用的规范（3 个 PR 出 1 条）。值得沉淀的规范更多藏在现有文档里、在反复出现的同类问题里、在人对 AI 代码的纠正里。
3. **跨项目共享要克制。** 最有价值的规则往往和具体业务强相关，比如 tuzi-api 的计费、资金规则，并不适合别的项目。复用通过维护者确认的跨仓库复制导入，副本各自演进。
4. **"自主开发"要设边界。** 目标定在边界清楚的中小任务。大需求先拆成多个 Issue，合并永远由人来。真实记录里，单个任务曾跑了 29.5 分钟，`go test` 整包超时（`DEV.md:325-329`）。
5. **先定义度量，否则飞轮转没转起来无从判断。** 至少要有四个指标：
   - 规则召回的准确率和覆盖率；
   - 审查意见被修复的比例和被撤回的比例；
   - AI PR 不经人改代码就被合并的比例；
   - AI PR 从提出到合并经过几轮。
6. **Health 不在核心闭环里。** 建议冻结，或者改造成"仓库画像"，见第 5 节。

## 2. 核心问题清单

### P0：挡住目标，或者带来系统性风险

**P0-1 知识闭环没验证过，没有反馈回路，提取器也是盲提**
- **证据**：
  - 真实规则里只有 1 条来自模型提取（`M1.md:144-149`）。
  - `review_findings` 存了规则 ID，但没有任何地方统计"某条规则被引用后，有多少次被修复、多少次被撤回"。
  - 提取器的输入只有 PR、文件、讨论和线索（`src/memory/decision.processor.ts:140-150`），没有现有规则。它输出的"例外于／替代"关系直接写进库里（`src/persistence/repositories/memory.repository.ts:43-44`），可模型从没见过任何规则 ID；"重复／冲突"两种关系被直接丢掉。
  - 批准例外时要求关联一条有效的原规则（`src/memory/memory.service.ts:293-296`），但管理页的编辑不允许修改例外关联（`src/admin/handler.ts:329`）。
  - 去重用的指纹包含规则原文（`memory.repository.ts:13-24`），换个说法就算一条新规则。
- **影响**：
  - Reply 判定"例外成立" → 形成线索 → 提取出例外候选 → 这条候选在管理页**批不了**，只能拒绝。
  - 同义规则在不同 PR 里反复出现。
  - 规则只增不减，回答不了"知识有没有让结果变好"。

**P0-2 仓库归属保持为规则边界（原多层模型建议已撤销）**
- `memories.repository_id NOT NULL`，唯一键是“仓库 + 来源指纹”。
- 跨项目通过人工确认复制导入；每条规则保留 must／should／info 级别。
- 用户决定不引入独立团队、继承、项目覆盖或提升。

**P0-3 两套执行引擎，开发任务不能恢复，而且绑死企微**
- **证据**：
  - 开发任务用单独的表和 Worker，每个 Bot 只有一个 leader（`src/development/store.ts:608-613`）。
  - 只有企微连接通过认证时才领任务（`src/development/worker.ts:211`）。
  - 重启时把运行中的任务直接取消（`store.ts:577`）。
  - 一个开发任务通常要几十分钟。
- **影响**：
  - 每次部署都会杀掉正在开发的任务。
  - 不通过企微就没法派任务，连 GitHub issue 里回复"开始"的任务也依赖企微连接。
  - 重试、状态、执行记录两套各写了一遍。

**P0-4 开发和审查之间的闭环在代码里是断开的**
- **证据**：
  - 开发 PR 直接跳过自动审查（`src/github/webhook/events/pull-request.ts:58-60`）。
  - 只有有仓库权限的"人"发评论才会触发修改（`pull-request-comment.ts:19`）。
  - 没有 CI 结果反馈。
  - PR 正文里的"验证："一行是 Agent 自己写的。
- **影响**：
  - AI 写的代码没有经过同一套规则的独立检查。
  - CI 失败要人去发现。
  - 最强的知识信号——人对 AI 代码的纠正——没有被采集。

**P0-5 执行隔离（接入多团队前必须解决）**
- **证据**：
  - Review 的 bash 可以在 PR head 上跑测试，等于执行了 PR 作者的代码（`REVIEW_RULES`，`src/review/agent.ts`）。
  - 开发 Agent 会装依赖、启动服务、访问任意网站。
  - 这些都和服务同一个系统用户，而服务启动时要从磁盘读私钥（`config.ts:101`）。
- **影响**：在单团队内部可以接受（用户已决定）。跨团队后，任何一个仓库有写权限的人都可能拿到所有安装仓库的写权限。

### P1：规模一上来就会出问题，或者是明确的缺陷

**P1-1 规则检索方式在规模化后会失效**
- Review 的做法是"范围命中的规则全带"，总量上限 3 万字符（`memory.service.ts:232,242`）。
- tuzi-api 一个仓库的候选集就有 50 条、653 行，路径大多是 `model/**`、`service/**` 这种宽范围，单仓库已经接近上限。
- 词重叠排序对"中文规则 vs 英文代码"近乎随机，项目自己的决策记录也承认了这一点（`HARDENING.md:100-105`）。
- Reply 和 Health 仍然按词重叠取前 10 条（`memory.service.ts:226`）。

**P1-2 作用域里的"条件"字段实现错误**
- Review 调用作用域匹配时传入的条件是空数组（`memory.service.ts:242`）。只要规则填了条件，就永远召不回来（`:289`）。
- 开发任务把规则自己的条件当作"已满足"（`src/development/rules.ts:46`），等于条件永远成立。
- 提取器的输出格式里明确要求填写条件，所以这不是边缘情况。
- 另外，提取器只要有一条候选不合格，整批都会作废。

**P1-3 预算衡量的是 token，不是费用；所有角色共用一个模型**
- 缓存读取按全额计入 token 总数（`src/pi/types.ts:20-27`，`src/pi/session.ts:184`）。
- 开发任务默认不限 token（`src/development/processor.ts:232`）。
- 模型名全局只有一个（`config.ts:117`）。
- 开发任务的 token 总数在 170 万到 334 万之间，但之前核对过，其中约 96% 是缓存读取，实际花费取决于缓存计价比例。现在的预算数字对费用几乎没有指示意义，也没法按角色挑选性价比合适的模型。

**P1-4 开发任务是一个长会话，没有计划关卡，也不能分阶段恢复**
- "判断要不要先问"和"动手写代码"在同一个可写会话里完成。真实记录里有一次拒绝开发就花了 169 秒、18k token（`DEV.md:175-179`）。
- 上下文压缩是关掉的，大任务会撞到上下文上限。
- 目标分支一有新提交，任务就放弃（`processor.ts:343`）。其实没有必要：提交的父节点就是基线 SHA（`src/github/client.ts:247`），PR 合并时由 Git 三方合并处理，不会覆盖别人的改动。活跃仓库里一小时的任务会经常因此白跑。

**P1-5 多仓库接入和权限运维**
- 加一个仓库要改环境变量 `GITHUB_ALLOWED_REPOSITORIES` 并重启（`config.ts:95`）。
- 管理接口的授权不检查白名单和撤销状态（`src/admin/repository.service.ts:43`）：已移除的仓库仍然能编辑规则、重新启用。
- 每次加载页面，都要对每个仓库逐个调一次 GitHub 权限接口，没有缓存。

### P2：结构性问题，不急

- **代码结构**：
  - `Database` 是一个继承 `JobRepository` 的大门面类，`JobAcceptor` 接口里混进了开发任务的方法。
  - `handler.ts` 职责混杂。
  - `review_mode`、`max_delegates` 两列已经没用。
- **Health**：
  - finding 的标识里包含 job ID，跨报告无法追踪同一个问题。
  - 默认分支没变也全量重跑。
  - 文件按字母序只取前 200 个。
  - 两次真实验收都是 partial。
- **领取任务的锁**：所有实例都排队等同一把全局 advisory 锁（`src/persistence/repositories/job.repository.ts:55,359`）。现在的规模没问题，仓库多了会成为瓶颈。
- **文档与代码不一致**：M3 清单里的迁移名、企微通知文档、`project-guide` 写的重试次数（3 次，代码是 5 次）。

## 3. 推荐的目标架构

### 3.1 原则

- **副作用全部由确定性的工作流执行。** Agent 只产出判断、代码和文字，不直接对外写。
- **只有一套执行引擎、一套 Agent 运行器、一套知识上下文服务。** Review 和开发共用。
- **知识分类管理，只有规范类知识需要人批准。**
- **每个闭环都要有度量。** 没有度量的机制不上线。
- **单代码库、单数据库。** 按"进程角色"拆部署，不拆微服务。

### 3.2 架构图

```
┌──────────────── 接入层（只做翻译，不执行任务）────────────────────┐
│ GitHub App(审查身份)  GitHub App(开发身份)  企微Bot  管理页/API     │
└──────────┬─────────────────────┬───────────────┬────────────────┘
           ▼ 事件／命令            ▼               ▼
┌──────────────────────── 控制面（确定性代码）──────────────────────┐
│ 租户与权限：Org/Team/Project、成员、身份映射、角色                  │
│ 工作流引擎：run/step、租约、重试、定时、人工等待、取消、并发键         │
│ 副作用网关：GitHub/企微写操作 = 幂等键 + 远端核对（发件箱模式）       │
│ 策略：Agent 权限档案、保护路径、风险关卡                             │
│ 模型网关：按角色选模型、按费用记预算、团队配额、用量账本               │
└──────┬────────────────────────┬────────────────────────┬────────┘
       ▼                        ▼                        ▼
┌─ 业务模块 ─────┐  ┌─ 知识面 ────────────────────┐  ┌─ 执行面 ───────────────┐
│ Review        │◄►│ 知识库：规则/决策/画像/案例    │  │ 工作区：仓库镜像缓存     │
│ Development   │◄►│ 上下文编译器（Agent 取知识的   │◄►│   + 每任务独立克隆      │
│ Insights(度量) │  │   唯一入口）                  │  │ Agent 运行器(Pi 进程)   │
└───────────────┘  │ 知识管线：信号→候选→整理→审批  │  │   在沙箱里跑            │
                   │ 规则度量与衰减                │  │ 确定性验证器(测试/扫描)  │
                   └──────────────────────────────┘  └────────────────────────┘
              PostgreSQL（含 pgvector） + 磁盘/对象存储（会话记录、补丁快照）

### 3.3 公共基础设施与业务模块

| 公共基础设施 | 独立业务模块 |
| --- | --- |
| 租户与权限、工作流引擎、副作用网关、模型网关、工作区管理、Agent 运行器与沙箱、上下文编译器、扫描器、会话记录与审计、渠道适配器（GitHub／企微／管理页） | **Review**：审查运行、意见生命周期、线程回复、发布策略<br>**Development**：任务、Issue 关联、计划、迭代、PR 关联<br>**Knowledge**：规则集、候选、审批、度量<br>**Insights**：看板和周报，吸收原 Health |

**这几块应该属于同一套系统。** 它们共用知识、身份权限、工作区与运行器、GitHub 写入；而且闭环本身要求紧密的数据关联：意见的结局要变成知识信号，开发 PR 要进审查。但它们应该是边界清楚的模块，不是一个大流程。

### 3.4 实体关系

```
Project（GitHub 仓库）1─* Rule 1─* RuleVersion
Principal（GitHub 登录 ↔ 企微 ID）─→ 仓库维护权限 / 开发角色
跨仓库导入 ─→ 目标仓库独立 Rule
Project 1─* PullRequest 1─* ReviewRun 1─* Finding ─(引用)→ RuleVersion
Project 1─* DevTask 1─1 Issue ; DevTask 1─* Iteration ─→ PR
Finding 结局 / Reply 结论 / 开发迭代 / CI 失败 ─→ KnowledgeSignal ─→ RuleCandidate ─→ RuleVersion
企微群 ─→ Project（按仓库配置）
```

### 3.5 部署形态，以及哪些东西不引入

- **两种进程角色。**
  - `edge`：Webhook、管理 API、渠道适配器、企微长连接。
  - `worker`：工作流步骤和 Agent。

  发布 edge 不会中断开发任务。worker 可以滚动重启，因为每个步骤都能恢复。
- **工作流引擎的选型。** 在 PostgreSQL 上自建一层：现有的租约、心跳、错误分类大部分可以复用。也可以评估 DBOS Transact（基于 Postgres 的 TypeScript 持久化工作流库）。不建议 Temporal，它需要单独运维一套集群。
- **不引入**：微服务、Redis/BullMQ、图数据库、独立向量库（pgvector 就放在同一个 PostgreSQL 里）、用大模型做编排。

## 4. 推荐的 Agent 架构

### 4.1 各 Agent 的职责与边界

| Agent | 触发 | 输入 | 输出 | 工具权限 | 上下文边界 |
| --- | --- | --- | --- | --- | --- |
| **Reviewer** | PR 打开或更新，**AI 的 PR 也审** | diff、固定快照、上下文包（规则／案例）、仍未解决的旧意见、扫描命中 | 意见、根因分组、规则引用、已检查的规则清单 | 读文件、codegraph、bash（沙箱、无网络），不能写 | 只拿到本 PR 和上下文包 |
| **Reply Triage** | 人回复本 App 的线程 | 原意见、线程、当前代码、该意见引用的规则 | 意见结局 + 知识信号 | 只读，bash 在沙箱里 | 单个线程 |
| **Knowledge Extractor** | PR 合并；信号批量汇总 | 证据包（diff、带身份的讨论、意见结局、修改历史）+ **最相似的 K 条现有规则（含 ID）** | 候选操作：新建／细化／例外／替代／合并／退役 | 只读，不需要 bash | 不能写规则 |
| **Planner**（开发第 1 阶段） | 任务受理 | 需求、Issue 讨论、仓库画像、规则索引 | 需要澄清的问题，或者计划：步骤、预计改动路径、验收标准、测试计划、风险标记、规模 | 只读 + codegraph | 不能写文件 |
| **Developer**（开发第 2 阶段起；修改迭代也是它） | 计划通过；或收到反馈：Review 意见、CI 失败、人的评论 | 计划、上下文包、工作区、反馈条目、上一阶段的交接摘要 | 工作区里的改动、PR 说明、交接摘要 | 编辑、写入、bash（沙箱，只能访问依赖源）、浏览器（沙箱） | 没有任何 Git/GitHub 凭据 |

### 4.2 为什么这样组织

- **多个专项 Agent 分头审查不值得做。**
  - 实测 token 是单 Agent 的 3–9 倍，耗时 2–3 倍，5 个样本里 3 个专项失败（[Review Agent 结构](../.agents/decisions/multi-agent-review.md)）。
  - 改成 Pi 单 Agent 之后，3 次运行都找到了以前只有专项才找到的扣款问题（`DEV.md:276-289`）。说明增益来自工具和读代码的深度，而不是角色拆分。
  - 以后如果还要加，最多加一个"高危意见复核"，并且要按现有约束用固定样本每个跑 3 次对比之后再定。
- **不需要一个当编排者的 LLM。** 编排就是状态流转，需要的是确定性；交给模型只会在最需要可靠的地方增加随机性和成本。
- **Planner 单独作为一次调用。** 原因有三：只读，不会在没想清楚时就动手；可以在动手前设关卡；计划会被保存下来，崩溃后能恢复。决定"先问清楚"时退出成本很低，不像现在要在可写会话里绕一圈。
- **Reviewer 审 AI 的 PR，这才是真正有用的多 Agent。** 两者上下文独立、用同一套规则，Reviewer 还可以换一个模型，减少两者在同一处看走眼。
- **提取器单独作为一次调用。** 它的时机（合并后、异步）、输入和输出都不同。关键改动是让它**看得到相似的已有规则**。
- **不设 Architect。** 架构理解来自仓库画像、知识库里的设计决策和 Planner 阶段。

### 4.3 哪些由 Agent 决定，哪些由服务强制

| 事项 | Agent 决定 | 服务强制 |
| --- | --- | --- |
| 读哪些代码、怎么改 | ✓ | 路径边界、保护路径、文件数和大小 |
| 规则是否适用（语义判断） | ✓（包括"条件"） | 提供了哪些规则、只能引用提供过的版本、必须检查的规则是否都看过 |
| 意见的严重度 | ✓ | 发布策略：行内还是总评、公开仓库隐藏高危细节 |
| 要不要先问清楚 | 提议 | 风险关卡：含迁移、改受保护路径、改动过大，由代码检测 |
| 跑测试 | 可以跑 | **有效的验证结果**以服务在干净检出上跑的为准 |
| 预算、超时、重试、取消、恢复 | — | ✓ |
| 提交、分支、PR、Issue、评论、通知 | — | ✓（经副作用网关） |
| 规则生效 | — | 只能由人通过服务批准 |

### 4.4 Skill、Tool、Agent、Workflow、Knowledge 的分工

| 概念 | 是什么 | 不是什么 |
| --- | --- | --- |
| **Workflow** | 持久化的步骤、状态、关卡、副作用，由代码实现 | 不由模型决定流程 |
| **Agent** | 一次有边界的模型会话：一个目标、一份上下文包、一个权限档案、一个输出格式 | 不持有长期状态，不直接对外写 |
| **Tool** | 由服务强制权限的能力（路径、网络、写入） | 不把对外有副作用的接口直接交给 Agent |
| **Skill** | 通用的做事方法（怎么审安全、怎么写 PR），按需读取 | 不是权限边界，不放项目规则，也不写评测答案 |
| **Knowledge** | 团队规则、决策、画像、案例，经上下文编译器提供 | 不写进 Skill 或 Prompt |

### 4.5 协作、拆分、并行、恢复与人工介入

- **状态**：全部放在工作流引擎里。Agent 之间不对话，只通过保存下来的产物交接：计划、意见、验证报告、交接摘要。
- **上下文**：每次调用都由上下文编译器重新生成。开发分阶段进行，每个阶段一个新会话，带上一阶段的结构化交接摘要，不依赖续接旧会话（上下文压缩本来就是关的）。
- **拆分**：Planner 判断超过阈值时（预计改动文件过多、跨多个模块、含迁移），输出子任务。服务据此建子 Issue 并记录依赖，每个子任务独立分支、独立 PR。**不在一个任务内部并行写代码。**
- **并行**：在任务之间并行。同一仓库按 Planner 预测的改动区域加并发键，区域重叠的排队。
- **重试**：沿用现在"按错误类型判断"的做法，另加"无进展检测"：连续两轮改动相同，或者同一个失败重复出现，就停下来转人工。
- **人工介入**：澄清需求、风险关卡处的计划批准、合并 PR、批准规则、随时取消，都是工作流里的"等待"状态，带超时和提醒。

## 5. 规则与知识体系设计

### 5.1 四类知识

| 类型 | 例子 | 来源 | 要人批准吗 | 生命周期 |
| --- | --- | --- | --- | --- |
| **规则**（可判定是否违反） | "资金变更必须幂等" | 文档导入、提取候选、人工编写 | 要 | 有版本，可替代、过期、退役 |
| **决策**（ADR，解释为什么） | "为什么日志库和主库分开" | 文档导入、合并 PR | 要（较轻） | 被替代为止 |
| **仓库画像**（事实） | 怎么装依赖、测试命令、模块地图、技术栈 | Agent 生成，再**实际运行命令校验** | 不要，可以人工修正 | 随默认分支变化重新生成 |
| **案例** | 已修复的问题、被撤回的误报 | 意见结局，自动记录 | 不要 | 自动衰减 |

仓库画像能直接省掉现在每个开发任务"自己摸索怎么装依赖、怎么跑起来"的时间，也可以取代 Health 的大部分用途。

### 5.2 数据模型

```sql
projects(id = GitHub 仓库 id, full_name, installation_id, default_branch, enabled, settings)
principals(id, github_login, wecom_userid)
role_bindings(principal_id, project_id, role)

rules(id, project_id, kind[constraint|decision|convention|exception|deprecated], status, current_version)
rule_versions(rule_id, version, status[candidate|active|superseded|retired|rejected],
  statement, rationale,
  applicability{paths, exclude_paths, languages, frameworks, modules, when /*自然语言条件*/},
  enforcement{level[must|should|info], default_severity},
  check_guidance, examples{violating[], compliant[]},
  provenance{kind[extraction|import|manual], refs}, evidence[],
  approved_by, approved_at, review_after, expires_at)
rule_relations(from_rule, to_rule, type[exception_of|supersedes|refines|duplicates|conflicts_with], status)

knowledge_signals(id, project_id, kind, refs, payload, at)
rule_candidates(id, project_id, op, target_rule_id, draft, signal_ids[], support, distinct_people,
                cluster_key, embedding, score, status, expires_at)
rule_usage(rule_id, version, project_id, run_id, event[provided|opened|cited|fixed|withdrawn|exception|applied], at)
decisions(...)
repo_profiles(project_id, sha, commands{install,build,test,lint}, verified{命令: 结果}, modules, stack)
```

和现在的做法相比，主要有三处不同：

- 把"规则"和"版本"拆成两张表。
- 关系用一张独立的表，以后可以加类型。
- "条件"改成自然语言字段，交给 Agent 判断，不再精确匹配。

### 5.3 仓库作用域与规则级别

上下文编译器用确定性代码计算本仓库实际适用的规则：

1. **收集本仓库规则。** 只取 ACTIVE 最新版本，候选更新不替代旧的有效版本。
2. **按适用范围过滤。** paths、languages、modules 匹配；自然语言条件交给 Agent 结合正文判断。
3. **带出例外依赖。** 例外须关联本仓库生效原规则，限定路径；同范围规则保留，编译器不推断语义冲突。
4. **排序并控制体量。** must 全部给出，超过上限告警；should、info 按相关度给正文，其余放进索引，Agent 需要时再读。

跨仓库复用沿用“从其他项目导入”，由目标仓库维护者确认，生成独立规则，不引入继承或提升。

### 5.4 提取流程

**信号**（采集都由确定性代码完成）：

| 信号 | 强度 |
| --- | --- |
| 人在审查中明确表态（统一用、以后、禁止……），并且合并的代码照做了 | 强 |
| 人对 **AI 写的 PR** 提出修改要求并被采纳 | 强（说明 AI 缺了这条知识） |
| 同类 AI 意见在多个 PR 里被修复（标记修复，或下次提交后消失） | 中，随次数增强 |
| AI 意见被撤回，并给出理由 | 中（反向知识：例外，或"这里别再报"） |
| 人提出修改要求 → 作者随后的提交改动了对应的行 | 中 |
| 回滚或热修复的 PR | 中 |
| 只有代码写法，没有人表态 | 不作为规则，可以放进画像里的"观察到的写法" |

**流程**：

1. 采集信号。
2. Extractor 拿着证据包和最相似的 K 条已有规则，输出**针对现有规则库的操作**，而不是孤立的新规则。
3. 确定性关卡过滤（见 5.5）。
4. 用向量把候选聚类，计算支持度：有多少个不同的 PR、作者、审查者支持它。
5. 进入**排序后的审核队列**。支持度低的候选不展示，60 天后自动过期。
6. 批准时检查冲突：先按适用范围重叠由代码判断，再由模型判断语义上是否矛盾。有冲突必须先处理才能生效。
7. 生成新版本，上下文编译器立即开始使用它。

### 5.5 怎样才算值得沉淀

Extractor 必须逐项填写，服务检查其中可以机器判定的几项：

1. **规范性**：能写成"在 X 情况下必须／禁止 Y"。
2. **可复用**：说明它适用于今后的哪些改动，不能只是在描述这个 PR。
3. **可判定**：审查者能从代码判断是否违反。要填写判定方法和正反例。
4. **有理由**：理由来自人的讨论或文档，不是模型推测。（服务检查）
5. **有人背书**：至少有一位维护者或审查者的评论，不能只有 PR 作者自己说。（服务检查）
6. **工具替代不了**：如果 linter 或类型检查就能强制，改为建议调整 lint 配置。
7. **说明和已有规则的关系**：新建、细化、例外、替代还是合并。（服务检查）

### 5.6 冲突、重复、过时，以及防止规则库膨胀

- **重复**：向量相似且适用范围重叠的，自动生成"合并"候选。
- **过时**由代码自动标记，进入复查队列：
  - **路径失效**：适用的路径在默认分支上已经不存在。
  - **沉睡**：180 天没被引用，而同期相关路径有不少 PR。
  - **噪声大**：样本至少 5 次，被撤回的比例超过 30%。
  - 到了复查日期或过期日期。
- **控制膨胀**：每个项目的 must 级规则设软上限；候选会过期；规则度量驱动退役队列。看的是质量，不是数量。

### 5.7 检索与复用：Review 和开发用同一个入口

上下文编译器根据"项目、任务类型、相关路径、文本"返回一个上下文包：

```
{ manifest:[{rule_id, version}],                 // 用于校验引用和审计（沿用现在的核对方式）
  rules_full:[...], rules_index:[{id, title, applicability, level}],
  conflicts:[...], decisions:[摘要], profile:{commands, modules},
  episodes:{同一文件上已修复的问题, 被撤回的误报} }
```

- **逐步提供**：一开始给索引，Agent 需要时调 `team_rule(id)` 读全文。读文件或写文件时自动附上相关规则——开发任务现在的做法（`src/development/rules.ts`）是对的，推广到 Review。
- **服务核对必须检查的规则**：Reviewer 输出"已检查的规则"清单，服务核对所有适用的 must 级规则是否都看过。没看过就触发修复轮。开发任务现有的 `missing()` 检查推广成同一套机制。
- **用到哪些地方**：Review 和 Developer 用同一个编译器、同一份规则；Reply 拿该意见引用的规则加上适用规则；Extractor 拿相似规则。
- **引入向量检索的依据**：项目自己的决策写的是"只有出现可测量的缺口才引入向量"，而 `HARDENING.md:100-105` 已经测出词重叠近乎随机。向量应该嵌入规则的判定方法和正反例，而不只是标题。

## 6. 核心工作流设计

### 6.1 多项目 PR Review 与规则沉淀

1. **事件进入。** Webhook 转成工作流命令，并发键是"仓库 + PR"。项目之间轮转调度，每个项目有并发上限，避免一个繁忙的仓库饿死其他仓库。
2. **准备。** 从仓库镜像建独立克隆并固定 SHA；运行扫描器；上下文编译器生成上下文包。
3. **Reviewer 审查。** 服务校验：路径、规则引用、必查规则的覆盖、分组完整性，失败时修复一轮。这些现有能力全部沿用。
4. **发布。** 发布前再核对一遍 PR 状态，然后经副作用网关发布（用现有的隐藏标记做远端核对，并推广到所有写操作）。记录这次提供了哪些规则、引用了哪些规则。
5. **回复。** 人回复 → Reply Triage → 更新意见结局 → 生成知识信号。
6. **合并。** PR 合并 → Extractor 产出候选操作 → 关卡 → 聚类 → 审核队列 → 批准时检查冲突 → 新规则版本。
7. **定期任务。** 汇总规则度量，产出复查队列：沉睡、路径失效、噪声大。

### 6.2 开发任务：从需求到 PR

```
① 受理   任何渠道（企微 / Issue 标签或命令 / 管理页 / API）→ DevTask
② 鉴权   需求人在该项目的角色；保存一份保护路径快照
③ Issue  每个任务都有 Issue（新建或关联已有的）。Issue 是任务的唯一事实来源，企微只做镜像通知
④ 计划   Planner（只读）→ 需要澄清的问题，或者计划
         - 需要澄清：贴到 Issue，等回复（沿用现在的"只回复有异议的编号 / 回复开始"交互）
         - 风险关卡（代码判断：含迁移、改受保护路径、改动超阈值）：等维护者批准
         - 规模过大：拆成子 Issue
⑤ 准备   分支名 ai/<issue>-<slug>；从只读镜像建独立克隆，检出基线 SHA；挂载依赖缓存
⑥ 实现   Developer 在沙箱里改代码；每 N 分钟把工作区改动存一份补丁快照
⑦ 关卡   从工作区收集改动（沿用 changes.ts）→ 保护路径、文件数和大小、密钥扫描、必须给出的规则是否都已给出
⑧ 验证   在"干净检出 + 套用改动"的新目录里，跑画像里登记的 lint、类型检查、测试
         → 失败就带着输出回到 ⑥，最多 K 轮
⑨ 发布   Git Data API 建提交（父提交 = 基线 SHA）→ 建分支 → 建 PR（Closes #issue）
         PR 的"验证"一段由服务按 ⑧ 的真实结果生成
⑩ 审查   这个 PR 走标准 Review（和人写的 PR 同一套规则、同一个 Reviewer）
⑪ 迭代   以下任一情况触发修改，在同一分支上追加提交，不强推：
         - Review 意见严重度 ≥ medium 且证据 ≥ moderate
         - CI 失败
         - 有权限的人发评论
         自动触发最多 2 轮，没有进展就停
⑫ 结束   合并 → 知识提取（包括人对 AI PR 的修改要求）→ 关闭 Issue；关闭未合并 → 记为负向结果
```

**分支和工作区**：隔离加提速的思路是对的，但不建议直接用 `git worktree`。所有 worktree 共用一个 `.git`（配置、钩子、引用），而 Agent 有 bash，能改共用的配置，影响其他任务。现在 `changes.ts:15` 专门防"Agent 改 `.git/config`"，说明这个风险真实存在。推荐的做法：

- 每个仓库在本地维护一个镜像，以只读方式挂载给任务。
- 每个任务用 `git clone --shared` 建独立克隆，向镜像借用对象。

速度和 worktree 差不多，`.git` 却完全独立。

**避免并行任务互相冲突**：

- 按计划里预测的改动区域加并发键。现在是同一仓库的开发任务一个一个来（`store.ts:161-172`），太保守。
- PR 阶段出现冲突时，服务把目标分支合并进开发分支（不强推）；有冲突就交给 Developer 作为一轮修改来解决。

**权限**：

- Agent 没有任何 Git/GitHub 凭据。
- 审查身份和开发身份用**两个 GitHub App**：审查的 App 只有内容读权限。分成两个身份后，开发 PR 的作者是另一个机器人，审查它很自然；分支保护也可以要求开发机器人的 PR 必须有人批准。

**恢复**：

| 故障 | 处理 |
| --- | --- |
| worker 崩溃 | 租约过期后重跑这一步（每一步都可以重复执行）；Developer 在新工作区套用最近的补丁快照接着做 |
| 发布 | worker 先停止领新任务，正在跑的步骤保存进度后释放，而不是取消 |
| 发布结果不确定 | 用确定的分支名和 PR 正文里的隐藏标记核对，不会重复创建 |
| 测试失败 | 有上限的循环，之后转人工 |

**提交内容和工作区一致**：

1. 提交由服务从工作区收集改动生成（沿用现有做法）。
2. 验证在"干净检出 + 套用改动"上进行，避免被未提交的生成文件掩盖问题。
3. 核对 PR head SHA（沿用现有检查）。
4. 最终以 GitHub 上的 CI 结果为准。

### 6.3 Review 反馈驱动修复和知识更新的闭环

```
人或 AI 提交 PR ──► Reviewer（规则来自上下文编译器）──► 意见（引用规则版本）
   ▲                                                     │
   │ AI 的 PR：Developer 修改（有上限）◄── 意见 / CI / 人的评论
   │ 人的 PR：人修改 ──► Reply Triage ──► 意见结局（修复 / 撤回 / 例外）
   │                                                     │
   └──── 合并 ──► Extractor（看得到相似规则）──► 候选 ──► 审核 ──► 规则新版本
                                                         │
          规则度量：引用后修复率 / 撤回率 / 沉睡 / 路径失效 ──► 降噪、退役
          被撤回的误报 ──► 案例 ──► 下次同一区域少报
```

## 8. 分阶段实施路线

**阶段 0：止血并补上度量（1–2 周，改动都不大）**
- **要做的事**：
  - 修"条件"字段的缺陷。
  - 提取器输入加入相似的现有规则；管理页允许设置例外关联；单条候选不合格只丢这一条。
  - 每次运行记录提供和引用了哪些规则；意见结局按规则汇总，在管理页展示。
  - 开发任务的领取和企微连接解耦。
  - 管理接口补上白名单和撤销检查。
  - 用量按"新输入 / 缓存读 / 输出"分开记录和计价，先只记录、不拦截。
- **验收标准**：
  - 带条件的规则能被召回（有回归测试）。
  - "例外"候选从线索到批准，端到端走得通。
  - 积累两周真实的"按规则统计的修复率和撤回率"。

**阶段 1：统一执行引擎（3–5 周）**
- **要做的事**：
  - 新的工作流相关表（运行、步骤、副作用、人工等待）。
  - 先迁移 Review、Reply、规则提取，再迁移开发任务。
  - 部署拆成 edge 和 worker 两种角色。
  - 开发任务支持补丁快照恢复。
  - 去掉"目标分支有新提交就放弃"。
- **验收标准**：
  - 在每个步骤上杀掉 worker，GitHub 上都没有重复写入，任务能接着做。
  - 部署期间，一个 30 分钟的开发任务不会丢。
  - 不经过企微也能派任务（管理页、API、Issue 标签）。

**阶段 2：知识模型 v2 和上下文编译器（4–6 周）**
- **要做的事**：
  - 仓库维护权限缓存，不重启就能接入新仓库。
  - 仓库规则、版本、关系、规则级别、度量。
  - Review、Reply、Developer 全部改用上下文编译器。
  - 候选聚类和排序审核队列，批准时检查冲突，衰减任务。
- **验收标准**（数值是初始目标，跑起来以后再校准）：
  - 规则提取评测集（至少 30 个人工标注的合并 PR）：准确率 ≥ 0.7。
  - 规则召回评测集：在给定的体量预算下，覆盖率 ≥ 0.9。
  - 仓库规则隔离生效，跨仓库复制导入照常工作。
  - 噪声大的规则会被自动标出。

**阶段 3：开发闭环 v2（4–6 周）**

> 用户 2026-11-15 决定：先不做阶段 3，集中做好阶段 1、2。理由：团队成员日常已经用本地 Codex／Claude Code 开发，服务自己的开发闭环相对它们没有优势；服务的价值在独立审查和团队规则。阶段 2 增加一项：把团队规则提供给本地 AI 工具。
- **要做的事**：
  - 每个任务都有 Issue。
  - Planner 阶段和风险关卡。
  - 分阶段的 Developer 会话。
  - 服务自己的验证，以及验证结果的 PR 段落。
  - 开发 PR 走标准审查，有上限地自动修改，CI 失败自动修改。
  - 人对 AI PR 的修改要求作为知识信号。
- **验收标准**：
  - 跑 20 个真实任务，统计合并率和平均修改轮数，并和阶段 0 的基线对比。
  - 没有出现重复的分支或 PR。
  - 每个 PR 的验证段都由服务生成。
  - 自动修改的循环都在上限内停下。

**门槛项：隔离与多团队（可以和阶段 1–3 并行，接第二个团队之前必须完成）**

> 用户 2026-11-15 决定：服务只在公司内部使用，不做这一项（独立系统用户、容器隔离、攻防测试、两个 GitHub App 都不做）。P0-5 的风险按现状接受。
- **要做的事**：
  - 第一层：Agent 用独立的系统用户执行，私钥和 `.env` 只有服务用户能读。
  - 第二层：每次运行一个无 root 容器，Reviewer 不能访问网络，Developer 只能访问依赖源。
  - 两个 GitHub App；团队配额；按角色选模型。
- **验收标准**：做一次攻防测试，Agent 用 bash 去读私钥、`.env`、数据库都失败；Reviewer 的网络限制确实生效。

**代价**（粗估）：
- **统一工作流引擎**：
  - 约 1.5–2.5k 行新代码，外加迁移五类任务。
  - 迁移期间两套引擎会并存，这是主要风险。
- **知识模型 v2**：
  - 约 3–4k 行，管理页加 3–4 个页面。
  - 每次合并多一次向量计算，成本很低。
- **隔离**：
  - 第一层约 100–300 行，外加部署脚本。
  - 第二层要按语言准备基础镜像、挂载依赖缓存、配置端口和浏览器。每次运行多 1–3 秒启动时间，本地起服务做验证的排障也会更麻烦。
- **开发闭环 v2**：
  - 每个任务多一次只读的计划会话，但能省掉"做到一半才发现要问"的浪费。
  - 每一轮自动修改要多一次 Review 和一次 Developer 会话，所以设了上限。
