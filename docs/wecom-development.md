# 企业微信群内 AI 开发

## 使用效果

每个群绑定一个仓库和目标分支。管理员或开发在群内 @ 智能机器人，发送开发描述，可在同一条图文混排消息中附截图。服务从目标分支的固定提交读取代码和全部已生效团队规则，生成新开发分支 `bot/development/<任务 ID>`，创建以配置分支为目标的 PR。

当前管理页每个仓库配置一个群。群 ID 不能绑定其他仓库。成员按仓库设置，用于开发权限；审查通知不需要成员关联。身份来自企微可信消息的 `from.userid`，不能在文字、图片或仓库文件中自称管理员。

- 管理员：可为本次需求修改受保护文件；原保护规则继续有效，不自动解除或修改。
- 开发：如果需求必须修改保护范围，或实际提出的改动命中保护规则，整项拒绝，不提交部分代码。
- 未配置身份：明确拒绝，不运行模型。

本服务创建的开发 PR 不触发本服务的自动 Agent Review，后续 `synchronize/reopened/ready_for_review` 也跳过；普通 PR 仍正常审查。PR 合并后仍保留原有 Decision Extraction 流程，规则候选仍需维护者确认。GitHub Actions、人工审查和分支合并条件不受此免审查设置影响，不自动合并。

完成后在原群引用发起任务的消息回复：

```text
AI 开发任务已完成
项目：owner/repository
PR：#123 修复订单计算
查看 PR（链接）
```

接收确认与完成结果通过同一原消息的回调标识分别发送，结果使用独立的流式消息 ID 并立即结束，保留原生引用关系；不会刷新已经结束的接收确认。消息展示状态、项目、PR 标题和独立链接，不写 `<@userid>`。引用用于对应原需求，不保证 @强提醒。拒绝、失败、取消、发布待核对会回复状态和原因。回调标识与 24 小时回复期限持久保存；重启后继续使用原标识，超过期限或缺少标识时明确记录失败，可在管理页查看结果，不伪装成引用或静默改发普通消息。发送结果不确定时不自动重发。

## 配置与管理

群内开发和 PR 审查通知都使用企业微信智能机器人 API 模式的长连接，不使用旧的 `WECOM_WEBHOOK_URL`，采用 [官方 Node SDK](https://github.com/WecomTeam/aibot-node-sdk)，无需增加公网回调 URL。

1. 创建智能机器人，启用 API 模式，选择长连接，取得 Bot ID 和 Secret，将机器人加入授权群。
2. 在被忽略的本地环境文件配置 `WECOM_BOT_ID`、`WECOM_BOT_SECRET`。所有实例使用同一配置。凭据不进入管理页、日志或 Git。
3. GitHub App 需要目标仓库 `Contents: Read and write`、`Pull requests: Read and write` 和 `Issues: Read and write`，并订阅 `Issue comment` 事件（需求 issue 用）。更改 App 权限后由安装方批准；仍使用 installation token，不用个人 PAT。若修改 GitHub Actions 工作流，还需要 GitHub 对该类操作要求的权限；权限不足会明确失败，不绕过。
4. 停止旧服务后执行 `npm run migrate`，应用增量迁移到 `012_development_issues.sql`，再构建和启动。已有数据库不能重跑 baseline。服务启动不自动迁移。
5. 在群里 @Bot 发一条文字；未绑定群的回复会给出群 ID。打开管理页「仓库 → 选择仓库 → 群内开发」，填写群 ID、目标分支、企微成员 ID 和角色，至少保留一名管理员，然后启用。
6. 在同一页面点「GitHub 账号关联」，把成员的企微 ID 和 GitHub 账号对应起来。需求 issue 里只认提需求的人关联的账号回复“开始”。
7. 在同一页面维护保护规则：名称、说明、文件／目录范围。范围支持精确相对文件、目录末尾 `/`、`目录/**`，以及 `**`（整个仓库）；不支持其他 glob 表达式。

管理页的设置操作要求该仓库的 GitHub maintain/admin 权限，并校验登录和 CSRF。企微管理员身份授权开发任务；管理页设置权仍由 GitHub 维护权限决定。每次保存设置保留操作人和完整设置审计，版本检查防止覆盖他人的更新。设置保存后未发布任务取消，需按新设置重新发起。

当前模型复用 `MODEL_*` 配置。带图片的任务要求支持视觉输入；自定义模型端点会声明并传递真实图片，端点不支持时任务失败，不把图片静默丢弃。`DEVELOPMENT_BUDGET_TOKENS` 默认留空，表示不限制 token（用量照常记录；设置后整个任务含重试共用这一额度）。开发任务的总时限是 `DEVELOPMENT_TIMEOUT_MS`，默认 1 小时，包含建 codegraph 索引和自动重试；审查类任务仍用 `AGENT_TIMEOUT_MS`。最多同时运行 `DEVELOPMENT_CONCURRENCY` 个开发任务（默认 3，范围 1–10）：不同仓库并行，同一仓库按发送顺序一个一个做。收到任务时回复“已收到开发任务”，同仓库前面还有未完成的任务时附上排队数量。图片限制为每条最多 4 张 PNG/JPEG、每张最多 2 MB、最长边 2048 像素；图片在接收时下载并解密，避免排队导致企微短期链接过期。下载只接受企微域名、HTTPS，禁止重定向，限制响应大小与时长。

## 规则和代码修改

任务读取该仓库全部 `ACTIVE` 团队规则并保存快照，按范围分两种方式交给模型：

- 没有路径、语言或模块范围的全局规则，在任务开头给全文。
- 限定范围的规则，开头只给编号、标题和范围组成的目录；Agent 用 read 读到、或用 edit / write 写入匹配文件时，服务在工具结果后附上规则全文。每条规则每个任务只给一次。
- 用命令新建的文件不经过写入工具：Agent 结束后，服务按收集到的改动路径检查，命中尚未给出的规则时用同一会话补发一次，要求按规则复核修改；补发后仍有遗漏则任务失败，不创建 PR。
- 规则的条件标签在开发任务中不参与匹配，由模型阅读正文理解。例外规则命中时，尚未给出的原规则一并附上。

服务附加的规则块以每个任务随机生成的标记开头，仓库文件中自称团队规则的文字仍按数据处理。快照为每条规则记录给出方式（任务开头、读取或写入某文件、结束后补发），便于排查未遵守的原因。Markdown 候选文档不会自动成为 ACTIVE 规则。此前整理的 tuzi-api 规则文档尚未导入，不应误认为已应用。

保护规则独立于普通团队规则，服务用完整保护集检查改动路径，不依赖语义召回命中率。管理员例外只作用于保护文件修改权限，其余团队约定仍用于指导开发。

开发 Agent 是一个 Pi 进程（见 [Pi Runtime 决策](../.agents/decisions/pi-runtime.md)），在目标分支固定快照的临时工作区里工作：用 codegraph、read、grep 弄清代码，用 edit 局部修改、write 新建文件，可以用 bash 运行编译、测试、lint 等检查。它加载服务的开发流程和提交规范 Skills，以及目标分支的仓库 AGENTS.md（参考）。Agent 拿不到 GitHub token，也不能访问其他任务目录。

写入时服务逐次检查：

- 开发身份写入受保护文件会被拦截；
- 覆盖已有文件前必须先 read 过，局部修改用 edit；
- 读取结果里有被打码的凭据时，这个文件只能用 edit 局部修改，不能整体覆盖。

## 需求 issue

需求有多种理解、缺少只有用户知道的值（金额、时限、文案、接口字段等），或要改数据库结构、对外接口、删除功能时，Agent 不改代码，由服务在仓库里开一个 issue：写它理解的需求、最多 3 个要确认的问题（每个带倾向的做法）、确认后的做法，末尾由服务注明谁回复“开始”才算数。群里回复“AI 开发任务需要先确认”和 issue 链接。

- **讨论**：issue 里人发的每条评论都会排一个“讨论回复”：Agent 读群里原话、issue 全文和目标分支代码（只读），在 issue 里回一条——回答问题、继续追问，或者说清最终做法。同一个 issue 的回复一次只跑一条；连续发了几条时只回最后一条（它会读到全部）。讨论回复不发群、不等同项目的开发任务。
- **开始**：提需求的人用关联的 GitHub 账号（管理页「GitHub 账号关联」，不区分大小写）回复一条只有“开始”“开始开发”“开工”或“/start”的评论，才排开发任务。别人说“开始”、没关联账号、讨论里顺口提到“开始”都不算，前两种会在 issue 里回一条提示。开发按当前的群内开发设置和提需求的人的身份（管理员／开发）检查保护规则；群内开发关闭或提需求的人不再是成员时，issue 不能继续。
- **开发**：Agent 拿到群里原话加 issue 全文，按讨论最后确定的做法开发。还有没定的，就把问题贴成 issue 评论，回到讨论中。PR 正文末尾加 `Closes #n`，PR 建好后在 issue 贴链接、在群里直接发消息（没有群消息可引用），管理页里最初开 issue 的那条任务改为成功并注明 PR 编号；没建成就把原因贴回 issue，可以调整后再说“开始”。开发中的 issue 再收到评论只回提示；PR 建好后不再处理评论。服务中断时开发中的 issue 回到讨论中。
- **写法**：issue、issue 回复、PR 正文都按 [commit-pr Skill](../agent/skills/commit-pr/SKILL.md) 写：大白话、短。服务检查字数（PR 正文 1000、issue 正文 800、issue 回复 500 字），超了在同一会话里让模型压缩一次。
- **限制**：开 issue 后群里原消息的图片不会带到之后的开发里，需要的话把图片贴进 issue 描述清楚；Agent 读的是 issue 的文字。

写代码时校验只放在系统边界，不为不会发生的情况加防护，会变的值照项目已有的配置方式放、不写死；按自己判断定下的取舍写进 PR 说明的“需要确认”一段。规则全文见 [development Skill](../agent/skills/development/SKILL.md)。

Agent 结束时只交 PR 标题、说明或拒绝原因。服务把工作区和快照比较，收集全部改动（Agent 自己 commit 也算，.gitignore 忽略的文件和 `.codegraph/` 不算），再检查一遍：最多 30 个文本文件、每个 200 KB；拒绝符号链接、子模块、路径越界、大小写或父子路径冲突、写回打码占位符、无实际变化；按最新权限重查保护范围。通过后用 GitHub Git Data API 基于快照创建 tree、commit、分支与 PR。

Agent 不安装依赖，bash 不访问网络服务；需要查网页资料或核对页面时可以用 Playwright 浏览器（无界面 Chromium、内存里的临时配置），能访问任意网站，网页内容按数据处理、结果同样打码，不在网站上做登录、发帖等外部操作（需求明确要求时除外）；它运行过的检查按范围概括写在 PR 正文最后的“验证：”一行里（含没跑的关键检查），只作参考，最终代码质量通过目标仓库 CI 和人工验收判断。目标分支在分析期间前进时取消任务，避免基于旧代码创建 PR。

## 幂等、取消与失败

- PostgreSQL 持久保存群绑定、角色、保护设置、任务、模型用量和通知状态。消息按 `(bot_id,message_id)` 去重。
- 一个 Bot ID 同时只有一个持有数据库会话锁的 Worker 连接企微并执行开发任务；领取时跳过已有任务在运行或发布中的仓库，所以同一仓库串行、不同仓库并行；现有审查 Worker 保持独立。
- 同时到达的消息最多两条并行接收（下载图片、入库），其余按到达顺序等待，不丢弃；等待超过 20 条才回复稍后重发。入库后的任务总数受 `QUEUE_CAPACITY` 限制。
- 任务进行中可在管理页开发任务列表展开“执行过程”看进度（每 5 秒刷新）：服务步骤（准备工作区、收集改动、规则和保护范围检查、确认目标分支、创建提交／分支／PR）和 Agent 的每次模型请求、工具调用在同一条时间线里，每次重试一条记录。服务中断后超过 2 分钟没有更新的记录显示“已中断”。
- Worker 数据库连接断开会取消活动任务；每个任务持有独立执行令牌，旧实例不能覆盖新实例恢复后的状态。每秒复核权限，发布各步前再次确认。
- 开发任务与旧 PR 审查可同时读取仓库，但都绑定各自的固定快照。开发不会修改已有分支，只创建任务专属新分支。
- 创建分支和 PR 前，数据库先保存预期分支和 head SHA。GitHub 创建回调先到时可以据此绑定 PR 归属并跳过审查，不能通过标题或标签绕过。
- 模型服务临时故障（限流、5xx、网关返回 `Upstream request failed`）时，整个任务在新的工作区里从头重试，最多执行 3 次，间隔 30 秒、60 秒；每次的用量累加进任务记录。开始创建提交、分支或 PR 后不再重试。额度用尽、认证失败等确定性错误不重试。
- 远端写入已开始后超时，仅做只读 PR 查询；可核对则记录成功，否则记录 `uncertain`，不再次创建。服务中断时未发布任务取消，正在发布的任务保留待核对。可能留下任务专属分支，管理员在 GitHub 核对后处理。
- 群通知发送前记录 `sending`；断网、进程中断或响应未知时保留 `uncertain`，不声称 exactly-once。消息未能送达时可在管理页查看 PR 和任务状态。

权限复核与外部 GitHub API 调用之间仍有短暂竞态，已经发出的请求不能撤回。角色变化不会删除已发布的 PR；所有结果均保留发起者及任务记录。

图片在任务结束时清除；文字需求、规则快照、用量、结果与 PR 归属随仓库生命周期保留，目前不应用普通审查任务的按日清理，避免清理后重新审查历史开发 PR。队列受 `QUEUE_CAPACITY` 限制；不要在群消息中发送真实凭据。

## 性能与验收

以下为路径计数估算，非线上压测结果：

- 未配置智能机器人时不启动开发 Worker，无额外数据库轮询或 WebSocket。
- 配置后每 Bot 一个长连接、一个数据库会话锁连接；空闲主实例每 2 秒约 3 次查询（探活、领取任务、领取通知），其他实例每 5 秒尝试一次领导锁。主实例额外每 4 秒约 1 次审查通知待发查询，未认证时不领取通知。
- 普通 PR Webhook 增加 1 次开发 PR 归属索引查询；任务专属分支首次回调最多增加 1 次归属绑定写入。
- 活动模型任务每秒约 1 次权限检查，模型请求前后各有用量持久化。执行过程记录有变化时每 5 秒保存一次（单行更新，内容最多 10 MB），没有变化时至少每 30 秒更新一次时间。文字和图片消耗均计入开发总预算，图片每张保守预留 32768 tokens。
- 限定范围的团队规则只在读到匹配文件时进入上下文；新建文件命中未给出的规则时多一轮模型请求，计入同一开发预算。规则匹配在内存中完成，不增加数据库查询。
- 一次正常发布通常为 installation token 1 次、目标快照检查两组各 3 次、tree／commit／ref／PR 各 1 次 GitHub API，共约 11 次 API，另加固定 SHA Git fetch。发布待核对时额外 1 次只读 PR 查询。
- 图片最多两条消息同时下载处理；每条最多四张，解密后的 Base64 总量上限约 10.7 MB，加下载缓冲和运行时开销。队列图片保存在数据库，不整批加载进内存。
- 发送按 Bot 串行并间隔至少 3.1 秒；接收确认、开发结果和审查通知共用该限速；审查通知独立轮询，不等待正在执行的开发任务。管理页仅在打开设置时加载配置和最近 50 个任务。
- 依赖新增官方 SDK；SDK 仅在服务端使用，不进入前端包。前端增加一个按现有页面入口加载的设置组件，构建产物测量与测试结果见任务清单。

真实验收需使用授权测试仓库和测试群，分别验证：开发普通任务成功、开发保护任务明确拒绝、管理员同一保护任务成功；文字加图片实际影响代码；PR base/head 正确且不产生 Agent 审查任务；结果原生引用任务提出者的原消息且 PR 链接可打开；普通 PR 审查完成通知直接进入绑定群且不含成员提及。记录 PR、任务 ID、时间、模型用量和接收方确认。自动化与真实验收分开记在 [开发任务清单](tasks/DEV.md)。
