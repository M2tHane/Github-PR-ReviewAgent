# Team Memory

## Context

PR 合并后的代码和讨论可能包含可复用的团队决定，但模型提取只能提出解释，不能代表团队授权。错误规则一旦进入后续 Review，会持续影响多个 PR；不同仓库的决定也不能相互泄漏。

## Decision

仅合并的 PR 触发 Decision Extraction。提取器依据合并快照、代码变化和人类讨论形成带来源的 `CANDIDATE`；具有该仓库维护权限的人通过管理界面确认后，规则才成为 `ACTIVE`。

维护者也可以从 Markdown 或有权限的其他项目预览规则，再明确确认导入为 `ACTIVE`。这条人工来源记录文件摘要或原项目规则版本、确认人和时间，不伪造 PR 证据或模型置信分数。跨项目复制为独立规则，例外关联必须在目标项目内重新建立；原有 PR 提取校验保持不变。

**规则有两级归属：项目和团队。** 团队由服务管理员建立并指定包含哪些仓库（一个仓库可以属于多个团队）；团队规则由团队管理员确认生效，对团队内所有仓库适用。没有单独的"全局"层级，需要全公司基线时建一个包含所有仓库的团队。项目维护者可以对继承来的团队规则做项目覆盖（停用或调整级别），必须写理由；项目规则可以作为团队规则的例外。项目规则可以"提升"为团队候选，团队管理员批准后原项目规则转为已替代。规则有级别：must 全部提供给 Agent，超过体量上限时告警而不截断；should、info 按相关度提供。

一个项目实际适用的规则由上下文编译器（`src/memory/context.ts`）用确定性代码算出：项目规则 + 所属团队规则 − 项目覆盖，按 Scope 过滤，例外按路径生效。项目差异通过项目例外（按路径生效）或项目覆盖停用（整个项目）表达；编译器不推断冲突。Review、Reply、健康检查、开发任务和规则提取都从这里取规则。

[MemoryService](../../src/memory/memory.service.ts) 通过编译器按归属、状态和 Scope 检索当前有效版本；[Review 校验](../../src/review/review.processor.ts) 再核对模型引用的 ID、version 和实际提供集合。候选修改生成新版本，待确认版本不自动撤销旧的有效版本。Reply 的解释只形成 clue，仍须经过提取与维护者确认。

## Why

模型的 confidence 衡量不了团队是否同意某项工程约束；自动激活会把误提取变成强规则。仓库权限与来源证据使规则的生效有明确责任人和可追溯依据。

当前先用归属隔离、Scope 过滤和轻量文本排序。VectorDB 会增加索引维护与跨仓库召回风险，只有召回评测集测出可测量的缺口时才引入。

团队共享是有意的：同一团队的仓库本来就遵守同一批约定，逐仓库复制会让同一条规则出现多份、各自演化。共享只发生在服务管理员明确划入同一团队的仓库之间，团队规则也要人确认，不会因为一个仓库的讨论自动扩散到其他仓库。

Review 的规则先按范围收集，再按级别与字符预算提供，must 不因体量被遗漏：中文规则和英文代码几乎没有词重叠，按分数取前 N 条时命中范围的规则带哪些接近随机。代价是首条提示变长、每轮请求都多算这部分预算。

## Constraints

- 模型不得创建、激活、替代或停用 `ACTIVE` Memory。
- Review 只接收上下文编译器为当前项目、当前 Scope 算出的 `ACTIVE` 版本；校验引用时以这次实际提供的清单（ID 与 version）为准，模型不能伪造 Memory 引用或来源。
- 规则只能在项目与它所属的团队之间共享；仓库移出团队后，团队规则立即不再适用于它。团队规则的确认、编辑、停用只能由该团队管理员或服务管理员操作。
- Review 对范围命中的规则（例外带出原规则）按项目覆盖后的级别排序：must 全部提供，超过字符上限也不截断，但记日志和 limitations；should、info 依次使用剩余额度，同级限定范围的优先，再按词重叠和 ID 排序。超出预算的规则作为索引提供，Review 可经服务工具按需读取全文；引用与 usage 只接受全文和本次成功读取的索引版本。Reply 和健康检查仍按原排序取前 10 条。
- 只有本次存在索引时才附加索引说明和读取工具，存在 must 时才附加检查要求；两者都没有时保留原有提示与工具。Review 必须逐条返回 must 规则的检查结论；缺失结论或违反结论缺少有效 finding 时，共用现有的一次修复轮。仍未确认的规则写进 limitations、日志和管理页计数，不阻止其余结果发布；这些检查记录不发到 GitHub。
- 保留人类评论与代码的来源校验、版本校验、仓库隔离和维护者权限检查。
- 例外规则必须限定 Scope 并关联仍有效的原规则：项目规则或本项目所属团队的规则。
