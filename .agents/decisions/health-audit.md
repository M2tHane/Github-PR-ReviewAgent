# Health Audit

## Context

PR Review 只看变更。仓库级健康检查需要默认分支及已有 CI 的证据，却没有真实 PR，也不应产生 GitHub Review。定时、重试和异常恢复还会影响任务去重与模型费用。

## Decision

Health 使用独立 `HEALTH_AUDIT` Job，固定仓库、默认分支 SHA、时间窗口和当时配置。[处理器](../../src/health/health.processor.ts) 只读受限的代码与已有 CI、Memory 资料；报告按 Job 唯一保存，与 Job 终态在同一事务提交，并在管理页查看，不向 GitHub 发布评论。

保持一个 Worker，领取时 PR、Reply 和 Decision 优先。定时只支持关闭、每日、每周且默认关闭；手动与定时触发共享活动任务去重。漏过的周期最多补一次当前检查。

每次模型请求前持久化预算预留，重试沿用同一 Job 的实际与未知消耗。报告明确实际读取范围、缺失数据和 limitations；趋势只比较口径相同且数据完整的指标。

## Why

复用 PR 字段会制造虚构 PR 和发布语义；独立任务与报告让生命周期清晰。当前周期简单、仓库数量有限，额外 cron 平台或 Worker 尚无收益。运行目标仓库测试或扫描需要不可信代码执行隔离，现阶段只使用只读证据。

## Constraints

- 不运行目标仓库代码，不修改源码、Memory 或 GitHub 评论。
- 不把无权限、无匹配 SHA、窗口外或截断的 CI 当作通过，也不把零 finding 当作完整覆盖。
- 重试不得重置预算；已取消、已替代或已存报告的任务不得被迟到结果重新激活或重复消费模型。
- 不生成综合健康分，也不因不可比报告自动宣称问题已修复。
- 依赖漏洞只按锁文件里写死的版本查询 OSV，记录由服务端直接写入报告；模型只能引用交给它的漏洞编号。查询会把"包名 + 版本"发到 api.osv.dev，私有仓库也不例外，可用 `VULNERABILITY_SCAN_ENABLED=false` 关闭。查询失败、不支持的锁文件和没写死的版本都记为缺失数据，不能当作没有漏洞。
- 密钥扫描结果只保存位置和类型。交给模型的文件内容、PR patch 和读文件工具的返回都先打码，报告与 PR 评论保存或发布前再按同一规则打码一次，防止报告本身成为泄露点。
- 代码规则扫描用 Semgrep 解析源码、按项目自带的 `rules/semgrep` 本地规则匹配，不构建、不运行仓库代码，也不读取仓库里的 Semgrep 配置、不联网。仓库文件名用 `--` 与选项隔开，Semgrep 在临时 HOME 下运行。命中只是候选，模型确认后才写成安全意见；没装 Semgrep 时记为缺失数据。
- 安全链路分析由独立的 Security Auditor 会话完成，与健康检查会话并行，按 65/35 分同一任务的剩余预算，两条 agent run 的消耗都计入重试扣减。服务端先用规则画攻击面地图作为线索；Agent 引用的入口、经过和危险操作每一行都必须是它实际读过的，否则整份链路结果丢弃并记为缺失数据。有入口到危险操作的完整链路才算 strong，追不到入口只能算 weak 并标注需人工确认。
