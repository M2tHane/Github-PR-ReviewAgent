# 执行引擎

## Context

Review、Reply、规则提取、健康检查走 `jobs` 表和 `PersistentRunner`（租约、心跳、按错误类型重试、停止时放回队列）；开发任务另有一套：`development_tasks` 自己领取，只在企微连接认证后、由持有 Bot 锁的实例执行，服务重启时把运行中的开发任务直接取消。开发任务通常要几十分钟，每次部署都会丢；不配企微就不能开发；重试、停止、恢复写了两遍。对 GitHub 的写入只有 PR Review 的发布有"幂等标记 + 远端核对"，线程回复、开发分支、PR、issue 评论在中断后要么重复、要么只能标成 `uncertain`。

## Decision

- **一个执行器，多个任务来源。** `PersistentRunner` 只管槽位、租约、心跳、停止和错误分类；任务从"来源"领取（`jobs` 表一个来源，`development_tasks` 一个来源），各自的领取条件和状态写回留在所属 repository。不新建通用的 run/step 表，也不把开发任务塞进 `jobs` 表：`jobs` 的约束是按 PR 设计的，开发任务的状态、通知、issue 关联都在自己的表里。
- **开发任务和企微解耦。** 开发任务由 worker 上的执行器领取，与企微连接无关；企微只负责收消息、回执和发通知。开发任务的来源可以是企微、GitHub issue（评论"开始"或打标签）、PR 评论、管理页和 API。
- **中断后接着做，不取消。** 租约过期（实例崩溃）或停止（部署）后任务回到队列，由任意 worker 接手：Agent 运行中定期把工作区改动存成补丁快照（存数据库），接手时在新工作区检出原基线、套用快照，再起一个新会话继续。崩溃计入尝试次数，部署停止不计。
- **对外写入走副作用台账。** 每个写操作有确定的幂等键；执行前先记"进行中"，成功后记结果。接手时遇到"进行中"先只读核对远端（分支是否存在且指向同一提交、按分支查 PR、按隐藏标记查评论），核对到就补记结果，核对不到才执行。PR Review 发布沿用现有台账。
- **进程角色。** `PROCESS_ROLE=edge|worker|all`（默认 `all`）。edge：Webhook、管理页与 API、企微长连接和通知；worker：执行器和定时任务。发布 edge 不影响正在执行的任务；worker 可以滚动重启。
- 开发提交的父提交就是基线 SHA，PR 合并时由 Git 三方合并处理目标分支上的新提交，不再因为"目标分支有新提交"放弃任务。

## Why

现有 `jobs` 执行器的租约、心跳、错误分类经过多轮验收，Review 类任务已经能在崩溃后由其他实例接手、靠发布台账避免重复发布。另起一套工作流引擎、再把五类任务迁过去，迁移期两套并存是最大的风险，收益只是统一表结构。真正缺的是：开发任务不能恢复、绑死企微、除 Review 发布外的写操作没有幂等。补丁快照比续接旧会话可靠（Pi 的上下文压缩是关的，旧会话也不在新实例上），新会话从工作区的实际改动继续即可。

## Constraints

- 每个对外写操作都必须有幂等键和只读核对方法；核对不了时保持 `uncertain`，不能盲目重发。
- 补丁快照只含按 .gitignore 过滤后的工作区改动，不含 `.git`；超过大小上限时不存并记日志，接手时从头开始。
- 停止时正在执行的任务放回队列，不计入尝试次数；租约过期计一次尝试，超过上限才失败。
- 企微回执与通知只能由持有该 Bot 连接的实例发送；没有企微来源的任务不发群通知。
